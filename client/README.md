# roomescape client

행사 탐색·신청·후기 서비스의 프론트엔드.

> **이 문서의 결정들은 확정이 아닙니다.**
>
> 백엔드 API 가 아직 만들어지는 중이라, 지금 구조는 "현재 있는 API 로 화면을
> 굴러가게 만든 상태"에 가깝습니다. 더 나은 방법이 보이면 여기 적힌 내용을
> 지키려 애쓰지 말고 바꾸세요. 다만 **왜 그렇게 했는지**를 아래 "설계 의도"에
> 적어뒀으니, 바꾸기 전에 그 이유가 아직 유효한지만 확인해 주세요.
>
> 바꿨다면 이 문서도 같이 고쳐 주세요. 문서와 코드가 어긋나는 게 제일 나쁩니다.

## 필요한 것

- Node 22+
- pnpm 10+
- **백엔드가 8080 포트에서 실행 중이어야 합니다**

## 실행

```bash
pnpm install
cp .env.example .env.local
pnpm dev
```

`http://localhost:3000` 으로 열립니다.

> ⚠️ **3000 포트를 바꾸지 마세요.** 백엔드 `SecurityConfig` 의 CORS 허용 목록이
> `localhost:3000`, `localhost:3001` 뿐입니다. 다른 포트로 뜨면 로그인이 CORS 에서 막힙니다.
> `vite.config.ts` 에 `strictPort: true` 를 걸어둬서 포트가 점유돼 있으면 다른 포트로
> 도망가지 않고 에러를 냅니다.

## 구현 현황

화면정의서 8분할 중 1번(홈)과 인증 관련 화면을 만들었습니다.

| 경로      | 화면       | 상태                                    |
| --------- | ---------- | --------------------------------------- |
| `/`       | 홈         | 레이아웃만. 검색바·추천 행사는 **정적** |
| `/login`  | 로그인     | 동작                                    |
| `/signup` | 회원가입   | 동작 (프로필 이미지 포함)               |
| `/mypage` | 마이페이지 | `내 정보` 탭만 동작                     |

### 아직 정적인 것

API 가 없어서 화면만 있는 부분입니다. **API 가 나오면 붙이면 됩니다.**

- 홈의 날짜·지역·날씨 검색바 (`disabled` 처리)
- 홈의 추천 행사 3개 (하드코딩, 이미지는 그라데이션으로 대체)
- 헤더의 공공행사 / 민간행사 / 커뮤니티 링크 (라우트만 존재)
- 마이페이지의 신뢰도 현황 / 내가 쓴 글 / 내 활동 탭

## 설계 의도

왜 이렇게 만들었는지입니다. 바꿔도 되지만, 바꾸기 전에 읽어 주세요.

### Access Token 을 메모리에 두는 이유

`localStorage` 에 넣으면 XSS 한 번으로 토큰이 통째로 털립니다. 그래서 모듈 변수에
두고, 새로고침으로 사라지면 HttpOnly 쿠키의 Refresh Token 으로 복구합니다.

**대가:** 앱 진입 시 `/auth/refresh` 를 한 번 호출하므로 첫 화면에 "불러오는 중…"
이 잠깐 뜹니다. 이걸 없애려고 `localStorage` 로 되돌리는 건 권하지 않습니다.

### 응답 봉투를 인터셉터에서 벗기는 이유

백엔드가 항상 `{ success, code, message, data }` 로 감싸서 줍니다. 벗기지 않으면
화면 코드마다 `res.data.data` 를 써야 합니다. `client.ts` 한 곳에서 벗기고,
호출부는 `client.get<unknown, T>()` 처럼 **두 번째 제네릭**에 실제 타입을 적습니다.

**주의:** 이 때문에 `client.ts` 의 성공 인터셉터에 캐스팅이 하나 들어 있습니다.
axios 타입상 `AxiosResponse` 를 돌려줘야 하는데 우리는 일부러 벗겨서 넘기기
때문입니다. 지저분해 보여도 의도된 것입니다.

### 기본 프로필 이미지를 파일로 만들지 않은 이유

R2 에 `default.png` 를 올려두고 그 key 를 저장하면, 모든 신규 회원이 같은 파일을
가리키는 의미 없는 참조가 생깁니다. 나중에 "기본 이미지인지 사용자가 올린
것인지" 구분하려면 key 를 문자열 비교해야 하고요.

그래서 `profileImg` 가 `null` 이면 **닉네임 첫 글자 + 색**으로 그립니다
(`shared/ui/Avatar.tsx`). 색은 닉네임 해시라 같은 사람은 항상 같은 색이 나옵니다.
파일도, 트래픽도, R2 요청도 들지 않습니다.

### 마이페이지의 "수정하기" 는 보안 장치가 아닙니다

기본은 읽기 전용이고 버튼을 눌러야 입력창으로 바뀝니다. **실수로 값을 건드리는
걸 막는 UX 장치일 뿐**이고, 백엔드 `PATCH /members/me` 는 토큰만 확인합니다.
API 를 직접 호출하면 이 단계 없이 수정됩니다.

원래는 여기에도 이메일 인증을 걸려고 했다가, 백엔드 변경이 필요해서 일단
보류했습니다. 실제로 막으려면 백엔드에서 "인증된 상태인지" 검사를 추가해야
합니다. (비밀번호 변경처럼 소모하지는 말고, 5분 동안 유지되게)

### 회원가입에서 이미지를 먼저 올리는 이유

```
① 업로드 → key
② 가입 (key 포함)
③ 자동 로그인
```

가입 시점에는 토큰이 없어서, 업로드 API 를 **비인증으로 열어둔 상태**입니다.
그래서 이 순서가 가능합니다.

> ⚠️ **누구나 인증 없이 파일을 올릴 수 있다는 뜻입니다.** 배포 전에는 반드시
> 막아야 합니다. 백엔드 `SecurityConfig` 에 TODO 로 남겨져 있습니다.
> 업로드 횟수 제한을 걸거나, 가입 API 가 파일을 직접 받도록 바꾸는 방향이
> 후보입니다.

### 휴대폰은 숫자만 저장하고 하이픈은 화면에서 붙입니다

`01023232323` 을 저장하고 `010-2323-2323` 으로 보여줍니다. 하이픈 유무가 섞이면
같은 번호가 다른 값이 되어 중복 검사나 발송 연동에서 문제가 생깁니다.

입력창은 **하나**입니다. 3칸으로 쪼개면 붙여넣기가 깨지고 브라우저 자동완성이
동작하지 않아서 오히려 입력이 느려집니다. (`shared/lib/phone.ts`)

### 비밀번호 변경이 3단계인 이유

백엔드가 `코드 발송 → 코드 확인 → 변경` 으로 나뉘어 있어 화면도 같은 순서입니다.
코드와 새 비밀번호를 한 번에 받으면, 코드가 틀렸을 때 비밀번호까지 다시 입력하게
됩니다.

### 폴더를 백엔드 domain 구조에 맞춘 이유

`features/auth`, `features/member` 는 백엔드의 `domain/auth`, `domain/member` 와
같은 이름입니다. 백엔드를 아는 사람이 "이건 어디 있지?" 를 묻지 않게 하려는
의도입니다. 새 도메인이 생기면 같은 규칙으로 추가해 주세요.

지금은 안 했지만 해야 하거나, 하면 좋은 것들입니다.

| 항목                                       | 이유                                                                       |
| ------------------------------------------ | -------------------------------------------------------------------------- |

## 인증이 동작하는 방식

### 토큰 두 개의 역할

| 토큰          | 저장 위치                        | 수명 |
| ------------- | -------------------------------- | ---- |
| Access Token  | **메모리** (`tokenStore`)        | 30분 |
| Refresh Token | **HttpOnly 쿠키** (JS가 못 읽음) | 14일 |

Access Token 을 `localStorage` 에 넣지 않습니다. XSS 로 통째로 털리기 때문입니다.
메모리라 새로고침하면 사라지는데, 앱 시작 시 `/auth/refresh` 를 한 번 호출해 복구합니다.

### 요청 흐름

```
요청 → Authorization: Bearer {accessToken} 자동 첨부
     → 401 AUTH202(만료)를 받으면
     → POST /api/v1/auth/refresh  (쿠키 자동 전송)
     → 새 토큰 저장 후 원래 요청 재시도
     → refresh 도 실패하면 토큰 폐기 (로그아웃 상태)
```

동시에 여러 요청이 401 을 받아도 refresh 는 **한 번만** 나갑니다
(`client.ts` 의 `refreshing` Promise).

### 응답 봉투를 벗깁니다

백엔드는 항상 이렇게 내려줍니다.

```json
{ "success": true, "code": "0000", "message": "", "data": { ... } }
```

인터셉터가 `data` 만 꺼내서 넘기므로, 화면 코드에서는 `res.data.data` 를 쓸 일이 없습니다.

```ts
const me = await getMyPage() // 바로 MyPageInfo
```

실패 응답은 `ApiError` 로 변환되어 `code` 와 `message` 를 그대로 들고 옵니다.

```ts
catch (e) {
  if (e instanceof ApiError && e.code === ERROR_CODE.INVALID_CREDENTIALS) { ... }
}
```

## 컨벤션

### 파일·폴더

| 대상     | 규칙         | 예                           |
| -------- | ------------ | ---------------------------- |
| 컴포넌트 | PascalCase   | `LoginPage.tsx`              |
| 그 외    | camelCase    | `client.ts`, `tokenStore.ts` |
| 폴더     | kebab-case   | `features/auth`              |
| 훅       | `use` 접두사 | `useAuth.ts`                 |

### 규칙

1. **컴포넌트에서 `axios` 를 직접 부르지 않습니다.** 반드시 `features/*/api.ts` 를 거칩니다
2. **타입은 백엔드 DTO 와 이름·필드를 그대로 맞춥니다.** `MyPageInfo` → `MyPageInfo`
3. **에러 코드 문자열 하드코딩 금지.** `ERROR_CODE` 상수를 씁니다
4. **import 는 절대경로** `@/features/auth/api`
5. **`any` 금지**

> `@/` 별칭은 `vite.config.ts` 의 `resolve.alias` 와 `tsconfig.app.json` 의 `paths`
> **두 곳에** 있습니다. 하나만 고치면 에디터나 빌드 중 한쪽이 깨집니다.

### 커밋

백엔드와 동일하게 쓰되 브랜치는 `front-` 접두사를 붙입니다.

```
feat: 로그인 화면 구현
fix: refresh 인터셉터 무한루프 수정

브랜치: feat/front-login
```

## 검증 항목

`pnpm dev` 후 아래 5개가 통과하면 인증 로직 전체가 검증된 것입니다.

- [ ] 로그인 → 마이페이지 정보 표시
- [ ] 새로고침 → 로그인 유지 (refresh 로 복구)
- [ ] 로그아웃 → 로그인 화면으로
- [ ] 틀린 비밀번호 → `[AUTH001]` 메시지
- [ ] 30분 방치 후 "내 정보 다시 조회" → 자동 재발급 (Network 탭에 refresh 요청)
